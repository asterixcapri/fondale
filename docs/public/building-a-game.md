# Building a game

The [quick start](quick-start.md) puts a Scene on screen and the [authoring
guides](README.md#build-a-game) give you every contract. This page gives you the
order: a pipeline of six skills that takes an idea to a playable short
adventure.

Three of them are interviews. They ask you what your game is and write the
answers into your own repository, each leaving the document the next one reads.
Three are fabrication, and they make artwork at the size those documents
decided. Between the two halves the game is built and played one ticket at a
time.

## Before you start

- **Your game's repository**, a TypeScript web project with
  `npm install fondale` already done. The skills read the Engine's
  contract out of `node_modules/fondale/docs/public/`, so what
  they read is always the version you build against.
- **An agent that runs skills**, and the `npx skills` CLI to install them.
- **ImageMagick 7** — the `magick` command on the PATH, from
  <https://imagemagick.org>. The fabrication skills crop and rescale every
  generated image with it. Nothing else in the pipeline needs it.
- **The skills.** Install Fondale's six from this repository, together with
  `fabrication-cycle`, which the three fabrication skills invoke, and the four
  they lean on but do not own:

  ```sh
  for skill in define-story define-puzzles setup-game \
      define-character define-scene define-object fabrication-cycle; do
    npx skills add asterixcapri/fondale --skill "$skill" -y
  done
  npx skills add mattpocock/skills --skill grilling -y
  npx skills add mattpocock/skills --skill to-tickets -y
  npx skills add mattpocock/skills --skill implement -y
  npx skills add openai/skills --skill imagegen -y
  ```

  Fondale's skills invoke `grilling` for the three interviews and `imagegen`
  for the images. `to-tickets` and `implement` run the construction and you
  start them yourself: no skill here starts them for you. Add
  `--agent <your agent>` when your harness needs to be named.

## The pipeline

Run these five commands in this order. Each skill declares what it reads and
writes in a `## Documents` table at the top of its own text, and ends by giving
you the next command to type.

| Step | Command | What it leaves in your repository |
| --- | --- | --- |
| Story | `/define-story` | `docs/game/story.md` — every place and how places connect, every Character, every Object, every Narrative Fact, under the names that become registry keys |
| Puzzles | `/define-puzzles` | `docs/game/puzzles.md` — one row per puzzle: what it needs, what the Player does, what changes — plus any row it has to add to `story.md` |
| Setup | `/setup-game` | `docs/game/world.md`, `docs/game/assets.md`, `docs/game/progress.md`, and a delimited section in your own `AGENTS.md` |
| Tickets | `/to-tickets` | one ticket per puzzle, read out of `story.md` and `puzzles.md` and ordered by real dependency |
| Implementation | `/implement` | the game, one ticket per session |

A skill whose input document is missing stops, tells you which command to run
first, and never runs it for you. You can re-run any of the three interviews
later: they revise their document in place rather than starting again.

`/setup-game` is where the scale stops being a matter of opinion. You declare a
**scale anchor** — one asset whose real size you can state, how many world units
it stands for, how many pixels tall it is — and every other asset's pixel target
is arithmetic from there. The section it writes into your `AGENTS.md` is what
tells `/implement` that a ticket is one playable puzzle, that the Engine's
documentation lives in the installed package, and that artwork is made by
invoking the fabrication skills rather than generated by hand.

## Making artwork

The fabrication skills are not a step of their own. `/implement` invokes them
whenever a ticket needs artwork, and you invoke them yourself afterwards
whenever you want to redo a Character or fix a Scene — six months later, without
replaying the pipeline.

| Command | What it produces |
| --- | --- |
| `/define-character` | a Character at the height `world.md` dictates, every Facing and Animation at that one height, and its `CharacterDefinition` |
| `/define-scene` | a Scene measured at 1:1, with its Walkable Region and Perspective Scale derived from `world.md`, and its `SceneDefinition` |
| `/define-object` | an Object sized beside the Character who carries it, its Inventory Appearance on the UI scale, and its `ObjectDefinition` |

Each of them invokes `fabrication-cycle`, which anchors the generation on the
artwork already made, normalises the result to its target height with the script
it ships, has you approve it at play size rather than as an isolated image, and
writes the measured height back into
`docs/game/assets.md`. That register is the memory of the whole process: whoever
makes the next asset finds the true size of the existing ones there, measured
rather than declared.

Two orders are fixed. **The first visual asset is the Player Character**,
because it is the anchor everything else is measured against. And **placeholders
come before artwork**: a Scene is built on a schematic Background at exactly its
final Scene Size, so the game is walkable long before it is beautiful and
finished art changes no authored coordinate.

## Where dialogue is authored

There is no dialogue skill, and none is missing. Dialogue in Fondale is
declarative data — knowledge with Disclosure levels, Cover Stories,
Relationships, authored alternatives — with a documented contract and a worked
example in [the dialogue guide](authoring/dialogue.md), so you author it from
that guide the way you author a Sequence or a Command Case. Games that route
free-form input to a backend also read the [Dialogue Provider
protocol](dialogue-provider.md).

The part that is genuinely hard — deciding who knows what, and who conceals it
by saying something else instead — is narrative design, and it is already done:
`/define-story` is where Narrative Facts and Claims are named, and
`/define-puzzles` is where knowing one becomes something the Player needs.

## How long this takes

A short adventure is roughly a dozen locations, ten Characters, twenty Objects
and one to two hours of play. Building one is weeks of evenings, not an
afternoon.

The three interviews are a working session each, and they are conversations
rather than typing. `/to-tickets` takes minutes. After that the cost is one
session per ticket and one ticket per puzzle, so ten to twenty sessions before
the game is playable end to end. The artwork is the long tail: a dozen
Backgrounds, and upward of a hundred Character frames once every Animation is
counted in four Facings, each one generated, normalised and approved.

What you can have early is the walkable game. Every Scene at its exact Scene
Size on a placeholder Background, every passage connected, every puzzle
playable — that arrives in the first handful of sessions, and none of the
artwork that lands later moves a single coordinate.
